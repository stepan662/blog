Durning spring and summer, I was having a career break due to a health issues. I knew it will be a longer recovery
so I thought it would be a good time to start some personal project and try new things.

## An old project

A few years ago I finished my Master degree with a durable orchestrator project.
It was a solution designed for my work, where we were dealing with long-running processes.
I had an idea in mind, however because of covid priorities changed and my project ended up unused and
not in a shape I imagined.

So now I thought, just for fun, why not to try re-implement the whole thing in a better way.
All that time in between this project was basically back in my mind, so I had quite a lot of
ideas how the project could be improved.

## The basic idea

Back in my old job, we were dealing with a heavily automated processes, with a human backup.
Basically the company was betting that it can automate about 90% of the stuff and the rest
will be done by humans.

We needed something that would connect our now scattered processes,
we had multiple services which were working mostly independently but there was no
central place which would keep track what was happening. There was some complex automation
if the automation fail it would send a message to some queue and it would be picked up by
a human agent, but nobody was keeping track that a human is now working on it (which was 
a part of the process) so if the automation was triggered again it could happen that the job
was done twice and it was hard to keep track of what is actually happening.

What we were missing was concept of durable process, we were just storing data - like
booking, user info etc. We were not storing the state of the process.

### Why not BPMN?

I had an opportunity to play with a BPMN execution tool and the concept was good,
but the actual experience was terrible.
Since BPMN is primarily a visualization tool, it was hard to understand
what the notation actually means in terms of execution. There are a lot
of concepts in BPMN like swimlanes, boundary events, parallel gateways, different kinds of messages etc.
And a fundamental feature of data passing between tasks is in the standard mostly as a drawing;
how it actually works is left to each engine and often feels like an afterthought.

### Existing non-BPMN systems

If we leave out BPMN, there are two kinds of approaches - code-driven and spec-driven.

Code-driven is something like Temporal.io you write your process as a code with some
durable primitives which will ensure your process can be recovered from permanent storage,
in case it crashes.

In Spec-driven systems, you don't use a general programming language
to write your process, you specify it's shape in a specialized syntax and the
process itself is mostly intended to connect different external systems together.
A typical examples here are AWS step functions (proprietary focused on AWS) or 
[Conductor](https://github.com/conductor-oss/conductor) (Opensourced solution from Netflix).

## The original concept

My master thesis project was code-driven - the process is basically a Typescript
code with some durable primitives - you have a checkpoints where you produce output which is stored, but in between you can execute what you want.

### The flaws

What I didn't like about this prototype was that it was language dependant - 
it forced the user to use Typescript. Also the engine itself needed to
wrap around some javascript runtime, which made it quite bulky.

One of my main concerns was the process should be reliable - meaning that if an
error happen it should be clear where and we should eliminate issues whith the
engine itself. If the process is code-defined we are giving the user a lot of surface
area for problems and then the error handling is very difficult.

## What would be ideal?

In my mind a durable process was simply a state machine. It is a sequence
of steps, each with defined output and every task can access outputs of previously
executed tasks.

The internal state would be stored in DB after each step and so it would be able to
survive server crashes and it would keep record of what happened.

### Passing data and validation

One of the most important features would be passing data from one task to another.
It needs to be easy to access previous task output. In my mind, the ideal would be
JSON - it's simple, easily serizable and human readable.

My other concern was validation, I hate when the system just accepts an external
data without validation. It always breaks somewhere later and you need to investigate
what was the source of incorrect data.

### Closest existing solution

The closest to this concept is probably [Conductor](https://github.com/conductor-oss/conductor),
the process is defined in JSON, the engine can call services over HTTP or let workers pick up tasks,
and data is passed between tasks with simple expressions. It even supports JSON-Schema validation
of task and workflow inputs and outputs. However the validation happens only at runtime - nothing
checks upfront that the output of one task actually fits the input of the next one.
It is also quite heavy - the server is a 458 MB Java jar, partly because it bundles
Python and JavaScript runtimes for inline scripts.



## The new concept

When I started working on the project again, my main idea was just create
a yaml defined state machine. The language of the state machine defintion
would be simple enough that it would be statically checkable.

If the user would want to have some complicated arbitrary logic,
it would needed to be outside of the engine. That keeps the engine small -
it's a single 15 MB binary.

### Refinement

As the prototype was growing, I've realized that static checkability will need to
also extend to data structures. I wanted to have every input validated and most
natural fit for me was JSON-Schema - it is language independent and well known.

I always liked the idea of validation schema also inferring resulting types
like [Zod](https://zod.dev/) does. So you validate all inputs and then have
static types based on that automatically.

I've realized I could use JSON-Schema as a basis for a type system and then
allow user to specify expressions which result would then be also typed (the types
would be inferred).

This turned out to be a defining feature of the project, strong statical analysys
basically eliminates runtime errors and it allows us to know exactly what
shape should the internal state have at any given point.

With this system it was also easy to build simple LSP for user and give a great
support for text editors (currently VSCode).

### Upgradability

If we can infer a JSON-Schema of the internal state at any given point, we
can allow user to upgrade instances from one version of the definition
to another. We just need to validate that the state of the instance
is valid for the new definition.

This also allows the system to detect breaking changes facing outside.
We can look at the inputs and outputs from the outside perspective and
look for breaking changes in the API and warn the user about that.
We can also use the inference system to enable the user to generate
JSON-Schema type of anything in the system. This is intended to be used
for validators of compatibility.

## Development style

I've decided to experiment with the AI driven development. At first I was checking
the code thoroughly and writing pieces myself, but slowly I've let the AI do more and more.
In the end I've settled on me deciding the architecture and the AI doing the coding.
But how do you ensure the code is honoring the architecture and it doesn't deviate?

What worked for me, was clearly defined and testable modules. For example, the typesystem
is testable separately so I can create a lot of unit tests with simple input/output.
And we can also test runtime, because the whole thing is a sate machine,
so we can easily check the internal state in between the steps.

There are many different kinds of tests, but these two methods
illustrate that you can get quite good insights into the functionality
of the system with a good test setup.

### The docs

I've written the documentation guides by hand and then
made the AI cross check it with the code, so that way I'm
trying to minimize misunderstandings between me and the AI.
